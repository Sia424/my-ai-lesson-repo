# 03．让 WorkBuddy 手把手教你注册 GitHub 账号

前两章认识了 Agent 的能力边界和安全常识。这一章开始做第一件真实的事：在 WorkBuddy 的帮助下，注册一个 GitHub 账号，并在你的电脑上配置好 SSH 登录。

读完并跟着做完本章，你会拥有：一个能正常使用的 GitHub 账号；一台配置好 SSH 登录的 Mac 或 Windows 电脑；以及第一次和 Agent 分工合作、完成真实任务的经验。

本章有两种用法，任选其一：

- **自己照着读**：按顺序阅读，每一步跟着做。涉及的命令都由 WorkBuddy 执行，你只需看懂大意。
- **交给 AI 带着做**：把本章全文发给你的 Agent（本章用 WorkBuddy 演示），再发送第 5 节的提示词。它会按本章的分工推进，在每一步告诉你它做什么、你做什么。

开始前确认四件事：

- 一台 Mac 或 Windows 电脑；
- 一个能正常收信的邮箱；
- 能打开 github.com 的网络；
- 已安装并登录 WorkBuddy（安装与登录见[官方入门指南](https://www.codebuddy.cn/docs/workbuddy/FirstTask)）。

## 1．GitHub 是什么

可以把 GitHub 理解成一个**全球公共档案馆，兼协作工位**。任何人都能在上面存放自己的文件、作品和项目；存进去的内容带着完整的修改历史，可以随时回看每一次改动，也可以选择公开，让别人浏览或参与协作。

先分清两个容易混淆的名字：

- **Git**：一个记录文件修改历史的工具，运行在电脑上。本教程不单独教它，暂时知道有这个东西即可。
- **GitHub**：使用和存放这些记录的网站，在浏览器里打开。你要注册和日常使用的，是它。

它和网盘的差别：网盘主要保存“最新版本”；GitHub 保存每一次修改的历史，天然适合需要积累、可能回看、也可能要公开的内容——比如你后续与 AI 协作写出的文稿、模板和整理好的资料。

GitHub 最早为程序员服务，如今也大量存放教程、笔记、文档和数据。你正在读的这本教程就存放在 GitHub 上，仓库地址是 [Sia424/my-ai-lesson-repo](https://github.com/Sia424/my-ai-lesson-repo)。

## 2．为什么你现在需要 GitHub

三个理由。

**它是 Agent 世界的“官方发布处”。**第二章强调过“优先官方来源”。对 AI 工具和开源软件而言，官方发布处通常就是一个 GitHub 仓库：安装说明、配置方法、更新公告都存放在那里。看得懂 GitHub，你才能找到一手资料，而不是依赖二手转述。

**它给你的成果一个长期的家。**后续章节会练习描述需求、组织项目和复用经验，这些练习产出的材料，以及你自己做的真实项目，都需要一个能长期保存、可回看历史、必要时可公开分享的地方。GitHub 同时解决这三件事。

**本章配置的 SSH 登录，是以后让 Agent 操作 GitHub 的钥匙。**现在花一点时间配置好，以后 Agent 帮你更新文件、保存成果时，不需要你每次输密码。

## 3．WorkBuddy 是什么，为什么好用

第一章把 WorkBuddy 列为候选入口，本章正式用它作为演示工具。

WorkBuddy 是腾讯的 AI Agent 办公工作台，有 Mac 和 Windows 桌面端，它能“自主规划、调用工具、生成文件，并把过程与结果都留给你审核”——这正是第一章对 Agent 的定义：能使用工具、根据执行结果继续推进任务的 AI 助理。

选它带你完成第一个任务，有四个理由：

- **图形界面**：像普通软件一样安装使用，不需要命令行基础。
- **能操作电脑**：可以打开网页、执行终端命令、处理文件，本章的大量步骤由它操作。
- **过程可审核**：它做了什么、结果如何都展示给你，涉及权限时需要你确认——正好实践第二章的审批意识。
- **中文界面、微信登录**：扫码即可使用，入门门槛低。

## 4．开工前：谁负责什么

这次任务由你和 WorkBuddy 分工完成，先看下分工表：

| 事项 | WorkBuddy 负责 | 你本人负责 |
|---|---|---|
| 注册账号 | 打开官方注册页，解释当前步骤 | 起用户名，输入邮箱和密码，完成人机验证与邮箱验证（如果有Google邮箱直接用Google邮箱登录，然后根据指引完成账号设置） |
| 本机 SSH | 检查环境，生成密钥，配置并测试 | 在安全输入窗口设置密钥口令，处理系统弹窗 |
| 添加公钥 | 复制公钥，打开设置页 | 确认账号，把公钥粘贴到 GitHub 并保存 |
| 完成验收 | 核对 SSH 返回的账号 | 核对返回的账号确实是自己的 |

三条安全原则，贯穿全程：

- 密码、验证码、恢复码和**私钥内容**，不进入聊天、截图或报告。
- WorkBuddy 可以调用密钥完成连接，但不能读取、打印或上传私钥内容。
- 公钥（文件名以 `.pub` 结尾）是可以公开的，把它交给 GitHub 没有问题。

为什么一把钥匙能公开、一把不能，第 7 节会解释。

## 5．把任务交给 WorkBuddy（提示词）

在 WorkBuddy 中新建任务，把本章链接或全文复制或导出文件发给它，再发送下面这段提示词：

```text
请带我完成本章任务：注册 GitHub 账号并配置本机 SSH 登录。
我使用的电脑是：Mac／Windows（二选一，删掉不用的那个）。

请按本章第 4 节到第 11 节的分工和步骤执行：
1. 先检查我的电脑环境和已有配置，再开始操作；保留现有的账号和密钥，不覆盖任何已有文件。
2. 密码、验证码、密钥口令和网页上的确认由我本人操作，不要让我把这些内容发到聊天里。
3. 需要我配合时，每次明确告诉我：打开哪个页面、做什么操作、完成后回复你什么。
4. 遇到我可能看不懂的命令或权限请求，先用日常语言解释，再执行。
5. 完成后按第 11 节的格式汇报结果；失败或未完成的项目如实标注。
```

整段提示词里，只有“我使用的电脑是”一行需要你改动，其余建议原样保留。几个关键句的作用：

- **“保留现有的账号和密钥，不覆盖任何已有文件”**：防止它改动你电脑上已有的配置。即使确定自己是第一次配置，这句话也没有坏处。
- **第 2 条**：把第二章的原则落实为规则——凭证永远不进聊天。
- **第 3 条**：约定配合方式，避免它一口气做完、不告诉你该做什么。
- **第 5 条**：要求如实汇报，不接受“全部完成”式的含糊总结。

如果不用 WorkBuddy 而用其他 Agent，这段提示词同样适用，把“本章”理解为这份文档即可。

发送后，WorkBuddy 会先检查你的电脑环境、说明它将做什么，再开始推进。接下来几节解释每个阶段发生什么、你在哪里出手。

## 6．注册 GitHub 账号

**WorkBuddy 来做**：用默认浏览器打开官方注册页。它执行的命令只是“打开一个网址”：

```sh
# Mac
open 'https://github.com/signup'
```

```powershell
# Windows（PowerShell）
Start-Process 'https://github.com/signup'
```

**你来做**：在打开的页面上按提示完成注册：

1. 输入邮箱，设置密码，起一个用户名；
2. 完成页面要求的人机验证（通常是拼图或选图）；
3. 到邮箱打开 GitHub 发来的验证邮件；
4. 选择免费（Free）个人计划即可，本教程用不到付费功能。

页面顺序可能随版本调整，以页面提示为准，也可参考 [GitHub 官方注册说明](https://docs.github.com/en/account-and-profile/how-tos/account-management/creating-an-account-on-github)。

两个细节：

- **用户名**是个人主页地址中 `github.com/` 后面那一串，不是显示昵称，也不是邮箱。它会出现在你的公开主页地址里，选一个你不介意公开的。
- 密码由你本人设置和保管，不要发进 WorkBuddy 的聊天。

**遇到问题**：收不到验证邮件，先查垃圾邮件和订阅文件夹，确认邮箱没输错；用户名被占用，换一个；页面打不开，先解决网络再继续。

**完成后告诉 WorkBuddy**：“账号已注册并验证，用户名是 XXX。”

**完成标志**：账号已注册、邮箱已验证、用户名已明确。

## 7．为什么要配置 SSH 登录

账号已经有了，为什么还要多配一步 SSH？

先说它是什么。SSH 是一种加密连接方式，让两台电脑安全地建立信任。用在 GitHub 登录上，可以打个比方：

- **账号密码**像每次进门都向门卫口头报一遍密码——报的次数越多，风险和麻烦越多。
- **SSH 密钥**像一对配套的锁和钥匙：**公钥**是锁，登记在 GitHub 那里，可以公开；**私钥**是钥匙，只存在你的电脑里，绝不外传。连接时，GitHub 用登记的锁验证你电脑里的钥匙，全程不传输密码。

配置它的三个好处：

1. **省事**：配置一次，以后在这台电脑上下载、上传 GitHub 的文件，不再需要输密码。
2. **更安全**：验证不依赖输入密码，私钥又不离开电脑，减少了密码被偷看、被钓鱼的可能。
3. **为 Agent 协作铺路**：以后让 Agent 更新 GitHub 上的文件时，它靠这台电脑上配好的钥匙工作，全程不需要、也不应该知道你的密码。

同时记住它的边界：SSH 只用于 Git 相关操作的验证，**不能替代网页登录**——浏览器里打开 GitHub 仍用账号登录；它**不会自动扩大权限**，你只能访问自己有权访问的仓库。

## 8．生成密钥：WorkBuddy 检查环境并操作

这一节 WorkBuddy 的工作量最大，你只参与一次：设置密钥口令。

**WorkBuddy 来做（检查环境）**：先确认电脑上有 Git 和 SSH 两个工具，并查看 `.ssh` 文件夹里是否已有别的密钥。主要命令在 Mac 和 Windows 上相同：

```sh
git --version
ssh -V
ssh-add -l
```

检查结果决定接下来的路：

- **缺 Git**：Mac 会安装 Apple 命令行工具（系统弹窗由你确认）；Windows 从 [Git 官网](https://git-scm.com/)下载安装包。
- **缺 SSH 命令**（只发生在较老的 Windows 10 上）：在“设置 → 应用 → 可选功能”中添加 OpenSSH 客户端，参考[微软官方说明](https://learn.microsoft.com/windows-server/administration/openssh/openssh_install_firstuse)；较新的 Windows 10 和 Windows 11 已自带。
- **已有 GitHub 密钥**：确认属于你且可用就直接复用，不重新生成；发现别人的或工作身份的密钥时，先问你要用哪个账号，并保留原有配置。

**WorkBuddy 来做（生成密钥）**：`.ssh` 文件夹不存在就先创建；确认下面两个文件名没有被占用——已存在同名文件就停下来检查，**绝不覆盖**。然后生成一对新的 ed25519 密钥（GitHub 当前推荐的类型），文件名特意带 `_github` 后缀，避免与其他用途混淆：

```sh
# Mac
ssh-keygen -t ed25519 -C "github-personal" -f "$HOME/.ssh/id_ed25519_github"
```

```powershell
# Windows（PowerShell）
ssh-keygen -t ed25519 -C "github-personal" -f "$env:USERPROFILE\.ssh\id_ed25519_github"
```

`-C` 后面的 `github-personal` 只是写进密钥文件的备注，帮你识别用途，不上传，也不是账号名。

**你来做（只此一次）**：命令会提示设置一个**密钥口令**。这是整个流程里唯一需要你亲手输入敏感信息的地方：

- 终端（Mac 的“终端”App，或 Windows 的 PowerShell——用文字命令和电脑对话的窗口）里，输入时**不显示任何字符是正常的**，输完直接回车，再输一遍确认；
- 口令保护的是电脑里的私钥，**和 GitHub 密码是两回事**，不要设成同一个；
- 建议设置口令。如果 WorkBuddy 无法让你安全输入，它会请你自己在终端运行上面那条命令——这是正常且更稳妥的做法。**不要**为了省事把口令发进聊天，或生成没有口令的密钥。

**完成标志**：`.ssh` 文件夹（Mac 在 `~/.ssh/`，Windows 在 `C:\Users\你的用户名\.ssh\`）里出现 `id_ed25519_github`（私钥）和 `id_ed25519_github.pub`（公钥）两个文件。

## 9．把公钥添加到 GitHub

这一节把“锁”登记到 GitHub，并让电脑记住钥匙。

**WorkBuddy 来做**：把公钥复制到剪贴板，并打开 GitHub 的密钥设置页：

```sh
# Mac
pbcopy < "$HOME/.ssh/id_ed25519_github.pub"
open 'https://github.com/settings/ssh/new'
```

```powershell
# Windows（PowerShell）
Get-Content "$env:USERPROFILE\.ssh\id_ed25519_github.pub" | Set-Clipboard
Start-Process 'https://github.com/settings/ssh/new'
```

**你来做**：在打开的页面上完成登记：

1. 先看右上角，确认登录的是你刚注册的账号；
2. `Title` 填一个便于识别的设备名，比如“我的 Mac”或“办公室 Windows 电脑”；
3. `Key type` 保持默认的 `Authentication Key`；
4. `Key` 一栏直接粘贴（公钥已在剪贴板），点 `Add SSH key`；
5. 页面要求输入密码或双重验证时，由你本人完成。

**完成后告诉 WorkBuddy**：“公钥已添加。”

**遇到问题**：提示 “Key is invalid”，多半是没复制完整。完整的公钥是**一整行**，以 `ssh-ed25519` 开头、中间一长串字符、以备注结尾；确认复制的是 `.pub` 结尾的公钥文件，而不是私钥。

**WorkBuddy 来做（让电脑记住钥匙）**：添加公钥后，它会让系统记住这把钥匙，以后使用时不再询问口令。Mac 和 Windows 的做法不同。

Mac 上，先把几行配置写进 `~/.ssh/config`（写入前备份你的原文件），再把口令存入系统钥匙串——需要你输一次口令确认：

```sshconfig
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_github
  IdentitiesOnly yes
  AddKeysToAgent yes
  UseKeychain yes
```

Windows 没有钥匙串，改为启用系统自带的 ssh-agent 服务并加载密钥。这一步需要管理员权限，WorkBuddy 会说明需要什么权限，你在系统弹窗里确认：

```powershell
Get-Service ssh-agent
Set-Service ssh-agent -StartupType Automatic
Start-Service ssh-agent
ssh-add "$env:USERPROFILE\.ssh\id_ed25519_github"
```

（Windows 上如果提示 ssh-agent 服务相关错误，回到这一步，让 WorkBuddy 检查服务是否启用后再试。）

配置每一行的作用不需要记，交给 WorkBuddy 处理；你只需在最终汇报里看到：**改了哪些配置、动了哪些文件**。依据：[GitHub 官方密钥生成与 ssh-agent 说明](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent)。

## 10．验证 SSH 登录

最后一步：确认钥匙和锁配对成功。

**WorkBuddy 来做**：执行测试命令，Mac 和 Windows 相同：

```sh
ssh -T git@github.com
```

**第一次连接会出现一个确认**：询问是否信任 GitHub 的主机指纹。WorkBuddy 应先对照 [GitHub 官方指纹页](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints)核对一致，再确认。这是防止连接被冒充的机制，和第二章“核对来源”是同一个道理。

**成功长这样**：

```text
Hi your-name! You've successfully authenticated, but GitHub does not provide shell access.
```

`your-name` 的位置应该显示**你的用户名**。后半句 “does not provide shell access” 不代表失败，只是说明 GitHub 不提供命令行终端服务；**这条命令的“退出码”为 1 也属于正常现象**，不应仅凭它判定失败。（判断依据：[GitHub 官方连接测试说明](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/testing-your-ssh-connection)）

**常见问题**：

| 现象 | WorkBuddy 的下一步 | 你需要做的 |
|---|---|---|
| `Permission denied (publickey)` | 逐项核对：密钥文件是否存在、是否已加载、公钥是否已添加、文件权限是否正常；不靠重新生成密钥碰运气 | 确认公钥添加到了正确的账号 |
| 连接成功，但返回的用户名不是你的 | 暂停，说明电脑上存在其他 GitHub 身份，先定位冲突 | 明确本次要用的账号 |
| 连接超时 | 记录失败的主机和端口，查阅[官方 443 端口方案](https://docs.github.com/en/authentication/troubleshooting-ssh/using-ssh-over-the-https-port)后再配置 | 必要时更换网络；不要关闭安全软件 |
| WorkBuddy 没有终端权限 | 说明受阻的命令和所需权限，保留已完成的步骤 | 授予相应权限，或由你执行那一条命令 |

## 11．结果检查与收尾

全部完成后，让 WorkBuddy 按下面的格式汇报，失败或未完成的项目如实标注，不写“全部完成”式的空话：

```text
GitHub 用户名：
账号注册与邮箱验证：通过／待用户完成
SSH 身份验证：通过／失败／未执行（附返回的用户名）
密钥文件路径：仅路径，不附私钥内容
SSH 配置变更及备份位置：
仍需我处理的事项：
```

你最后核对一件事：汇报里的用户名，和你注册后告诉它的用户名一致。

回看这次协作，第二章的原则全都用上了：密码和口令没进聊天；每一步谁做什么、需要什么权限都清楚；结果不靠“感觉完成了”，而是有一条能核对的判据。这就是一次标准的“带着边界使用 Agent”。
